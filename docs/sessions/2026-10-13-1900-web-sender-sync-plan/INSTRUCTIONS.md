# Οδηγίες: συγχρονισμός FortioMobile με το Fortio web (αποστολέας)

Αυτό το αρχείο είναι για τον agent που θα κάνει τη δουλειά στο FortioMobile. Η περίληψη για τον χρήστη είναι στο `mobile-sync.html`, στον ίδιο φάκελο.

- Ημερομηνία σύγκρισης: 13/10/2026
- Fortio web: `main` στο commit `0edf54a`
- FortioMobile: `master` στο commit `5478681`
- Τελευταίος συγχρονισμός του mobile: 28/9/2026 (`docs/sessions/2026-09-28-1919-sync-web-sender-changes`)

Η σύγκριση έγινε διαβάζοντας τον κώδικα των δύο εφαρμογών. Δεν έχει δοκιμαστεί σε συσκευή. Πριν αλλάξεις κάτι, επιβεβαίωσε στον κώδικα ότι ισχύει ακόμα αυτό που γράφεται εδώ.

## Κανόνες

1. Διάβασε πρώτα το `CLAUDE.md` του FortioMobile. Ισχύει ολόκληρο.
2. **Μην αλλάξεις κανένα αρχείο στο `C:\Users\CSKIN\Fortio`.** Το διαβάζεις μόνο, για να δεις συμβόλαια API και πώς το έκανε το web.
3. Το mobile είναι μόνο για τον αποστολέα. Τίποτα από τον μεταφορέα δεν μεταφέρεται.
4. Κάθε νέο κείμενο μπαίνει στο `lib/i18n.tsx` και στις **τρεις** γλώσσες (el, en, fr).
5. Μετά από κάθε εργασία τρέξε `npx tsc --noEmit`.
6. Μην κάνεις commit ή push αν δεν το ζητήσει ο χρήστης.
7. Στο τέλος γράψε τον φάκελο συνεδρίας που ζητά το `CLAUDE.md` (`commands.md`, `changes.md`, `errors.md`).
8. Απάντα στον χρήστη στα Ελληνικά.

## Αποφάσεις που περιμένουν τον χρήστη

Ρώτα τις **πριν** ξεκινήσεις την αντίστοιχη εργασία. Μην υποθέσεις απάντηση.

| # | Ερώτηση | Επηρεάζει |
|---|---|---|
| 1 | Έγινε στο Fortio η αλλαγή του `/api/routes/[id]/request` ώστε να δέχεται το token του κινητού; | Εργασία 2 |
| 2 | Η κάρτα μετακόμισης να είναι πλήρης όπως στο web, ή απλή έκδοση; | Εργασία 6 |
| 3 | Να φύγει η «Νέα Αποστολή» από το μενού ≡ του κινητού; | Εργασία 3.6 |
| 4 | Να κρύβεται η «Έρευνα Δρομολογίου» για μετακόμιση και κάδο; | Προαιρετικό |

### Η αλλαγή του API (απόφαση 1)

Το `app/api/routes/[id]/request/route.ts` του Fortio χρησιμοποιεί `getServerSession(authOptions)`. Το mobile στέλνει `Authorization: Bearer <token>`, άρα θα πάρει 401. Τα υπόλοιπα endpoints που χρειάζεται αυτό το πλάνο χρησιμοποιούν ήδη `getApiUser` και δέχονται το token.

Η αλλαγή γίνεται **σε συνεδρία του Fortio**, όχι από εδώ. Αν δεν έχει γίνει, πες το στον χρήστη και προχώρα με τις εργασίες που δεν εξαρτώνται από αυτήν (1, 3, 4, 5). Δοκίμασε το endpoint με πραγματική κλήση πριν θεωρήσεις ότι δουλεύει.

## Βοηθητικά που θα χρειαστούν παντού

Φτιάξε τα μία φορά (π.χ. στο `lib/display.ts` ή σε νέο `lib/shipmentKind.ts`) και χρησιμοποίησέ τα σε όλες τις οθόνες.

```ts
export const isMoveCategory = (c?: string | null) => c === 'HOUSE_MOVE'
export const isBinsCategory = (c?: string | null) => c === 'WASTE_BINS'
export const isCardCategory = (c?: string | null) => isMoveCategory(c) || isBinsCategory(c)

// Είδος προτύπων από την κατηγορία της αποστολής (ίδιο με το web: lib/templates.ts → templateKindForCategory)
export type TemplateKind = 'TRANSPORTS' | 'MOVES' | 'WASTE_BINS'
export const templateKindForCategory = (c?: string | null): TemplateKind =>
  c === 'HOUSE_MOVE' ? 'MOVES' : c === 'WASTE_BINS' ? 'WASTE_BINS' : 'TRANSPORTS'
```

## Εργασίες, με τη σειρά που προτείνεται

### Εργασία 1 — Πρότυπα ανά είδος μεταφοράς (κρίσιμο)

**Πρόβλημα.** Το `/api/templates` επιστρέφει πλέον πρότυπα τριών ειδών. Το mobile δεν στέλνει `kind`, οπότε σε κανονική μεταφορά εμφανίζονται και τα πρότυπα «Μετακόμιση : …» και «Κάδος : …».

**API.** `GET /api/templates?role=SENDER&kind=TRANSPORTS|MOVES|WASTE_BINS`. Με `kind` φιλτράρονται και τα έτοιμα και τα δικά μου. Η σειρά (`sort_order`) εφαρμόζεται από το API.

**Τι να κάνεις**
- `lib/templates.ts`: το `useMessageTemplates(role, category, kind)` να δέχεται `kind` και να το προσθέτει στο URL. Να μπει και στις εξαρτήσεις του `useEffect`.
- `components/TemplateSendModal.tsx`: νέο prop `kind`, που περνά στο hook.
- `app/(tabs)/index.tsx`: το `TemplateSendModal` να παίρνει `kind={templateKindForCategory(tplFlow?.shipment?.category)}`. Έλεγξε ότι το `tplFlow` κρατά την αποστολή με την κατηγορία της.
- Στο ίδιο αρχείο, ο πίνακας `TPL_FLOW_CATEGORY`: για `loadCancel`, όταν η αποστολή είναι μετακόμιση ή κάδος, η κατηγορία είναι **`OFFER_CANCEL`**. Για τις κανονικές μεταφορές μένει `OFFER_CANCELL_BEFORELOAD`.
- `app/(tabs)/shipments/matches/[id].tsx`: τα πρότυπα του αιτήματος να φορτώνονται με κατηγορία `REQUEST` και το είδος της αποστολής. Σήμερα φορτώνει όλα τα πρότυπα του αποστολέα.
- `app/(tabs)/messages/[offerId].tsx`: το είδος από την αποστολή της συνομιλίας.

**Έλεγχος.** Σε κανονική μεταφορά, η «Ακύρωση αιτήματος» δείχνει ένα πρότυπο και όχι τρία. Σε αποστολή μετακόμισης δείχνει το «Μετακόμιση :Ακύρωση Αιτήματος Προσφοράς».

### Εργασία 2 — Κάρτες μεταφορέα στα αποτελέσματα (κρίσιμο, θέλει την απόφαση 1)

**Πρόβλημα.** Για `HOUSE_MOVE` και `WASTE_BINS` το API επιστρέφει `routes: []` και τις κάρτες στο `cards`. Το mobile διαβάζει μόνο `routes`, άρα η οθόνη είναι άδεια.

**API**

```
GET /api/shipments/{id}/matches
→ {
    routes: RouteMatch[],
    cards: { id: string; cardId: 'MOVE' | 'WASTE_BINS'; title: string; companyName: string; offerStatus: string | null }[],
    hiddenCards: { id: string; cardId: string; title: string; companyName: string }[],
    matchCount: number, ...
  }

POST /api/routes/{cardId}/request      body: { shipmentId, content? }   → 201 (η προσφορά)
POST /api/card-exclusions              body: { routeId: cardId, shipmentId }   → { ok: true }   («Δεν με ενδιαφέρει»)
DELETE /api/card-exclusions            body: { routeId: cardId, shipmentId }   → { ok: true }   («Επαναφορά»)
```

- Το `offerStatus` είναι `null` όταν δεν έχει γίνει αίτημα, `'REQUEST'` όταν έχει σταλεί, και οτιδήποτε άλλο όταν ο μεταφορέας έχει απαντήσει.
- Το `content` είναι το κείμενο του προτύπου. Ο server το αποθηκεύει ως μήνυμα του αιτήματος. Χωρίς `content` μπαίνει ένα προκαθορισμένο κείμενο.
- Τα σφάλματα έρχονται ως `{ error: string }` με κωδικό 4xx. Δείξε το `error` στον χρήστη.
- **Μην** στείλεις αίτημα σε κάρτα μέσω του `/api/messages`. Η κάρτα θέλει το δικό της endpoint, γιατί ο server δημιουργεί την πραγματική εγγραφή της αποστολής κάτω από την κάρτα.

**Τι να κάνεις**
- `lib/api.ts`: τύποι `CardMatch`, `HiddenCard`. Το `matchesApi.get` να επιστρέφει και `cards`, `hiddenCards`. Νέες μέθοδοι για αίτημα σε κάρτα, απόκρυψη και επαναφορά.
- `app/(tabs)/shipments/matches/[id].tsx`:
  - Λίστα καρτών πάνω από τα δρομολόγια: εικονίδιο (🗑️ για `WASTE_BINS`, 🏠 για `MOVE`), τίτλος, όνομα εταιρείας.
  - Χωρίς `offerStatus`: κουμπιά «Δεν με ενδιαφέρει» και «Αίτημα Προσφοράς». Με `'REQUEST'`: «✓ Αίτημα Εστάλη». Αλλιώς: «✓ Λήψη Προσφοράς».
  - Το «Αίτημα Προσφοράς» ανοίγει το ίδιο παράθυρο προτύπων με τα δρομολόγια (κατηγορία `REQUEST`, είδος της αποστολής) και στέλνει στο νέο endpoint. Σε αποτυχία το παράθυρο μένει ανοιχτό και δείχνει το σφάλμα.
  - Ενότητα «Κρυμμένες» με κουμπί «Επαναφορά», όταν υπάρχουν `hiddenCards`.
  - Μετά από επιτυχημένο αίτημα, `invalidateQueries` για `['matches', id]` και `['dashboard-sender']`.
- Ο αριθμός στον τίτλο να μετρά `routes.length + cards.length`.

**Αναφορά web.** `app/shipments/[id]/matches/page.tsx` (οι συναρτήσεις `requestCard`, `setCardHidden` και η απόδοση των καρτών).

**Έλεγχος.** Αποστολή μετακόμισης με κάρτα που ταιριάζει: εμφανίζεται η κάρτα, το αίτημα στέλνεται, και στο dashboard η αποστολή περνά στα «Αιτήματα Προσφορών».

### Εργασία 3 — Κείμενα και εμφάνιση

Όλα αφορούν μετακόμιση και κάδο. Οι κανονικές μεταφορές μένουν όπως είναι.

1. **Κουμπί στο dashboard** (`dash.btn.routes`): «Μεταφορείς» για μετακόμιση, «Προμηθευτής» για κάδο, αλλιώς «Δρομολόγια».
2. **Οθόνη αποτελεσμάτων**: τίτλος «Διαθέσιμοι Μεταφορείς» ή «Διαθέσιμοι Προμηθευτές» αντί για «Διαθέσιμα Δρομολόγια». Στη φόρτωση: «Παρακαλώ περιμένετε» και από κάτω «Αναζήτηση και Φόρτωση Στοιχείων».
3. **Γραμμή προσφοράς στο dashboard** (καρτέλες Αιτημ. Προσφορών, Προσφορές, Παράδωση, Μεταφορά, και το παράθυρο προσφοράς):
   - Να μη φαίνεται η διαδρομή και οι ημερομηνίες του «δρομολογίου» της προσφοράς. Για κάρτες είναι αντίγραφο της ίδιας της αποστολής.
   - Εικονίδιο 🏠 ή 🗑️ αντί για 🚛, και μετά το όνομα « · Μεταφορέας» ή « · Προμηθευτής».
   - Κάτω από την τιμή, η πρώτη γραμμή του `offer.message`, κομμένη σε μία γραμμή. Όχι στα αιτήματα, γιατί εκεί το μήνυμα είναι του ίδιου του αποστολέα.
4. **Γραμμή τοποθεσίας της αποστολής**:
   - Μετακόμιση: `originAddress → destAddress`. Αν λείπει διεύθυνση, πόλη/χώρα όπως τώρα. Χωρίς χιλιόμετρα.
   - Κάδος στο dashboard: `destAddress (N μέρες)`. Η ημερομηνία φαίνεται ήδη στην επικεφαλίδα. Αλλού: `destAddress - ημερομηνία (N μέρες)`.
   - Το `N` είναι το `cardDetails.durationDays`. Αν λείπει, δεν μπαίνει παρένθεση.
   - Το `GET /api/dashboard/sender` επιστρέφει πλέον `originAddress`, `destAddress`, `cardDetails`. Πρόσθεσέ τα στον τύπο `Shipment` του `lib/api.ts`.
   - Αναφορά web: `lib/shipmentPlaces.ts`.
5. **Οθόνη Πρότυπα** (`app/(tabs)/templates.tsx`): τρεις επιλογές «Δρομολόγια», «Μετακόμιση», «Κάδοι» πάνω από τη λίστα. Η επιλογή στέλνεται ως `&kind=` μαζί με το `raw=1`. Προεπιλογή «Δρομολόγια».
6. **Μενού ≡** (απόφαση 3): αν ο χρήστης πει ναι, αφαίρεσε τη «Νέα Αποστολή». Το κουμπί + στο dashboard μένει.

### Εργασία 4 — Φόρμα αποστολής: πεδίο και τίτλοι

`app/(tabs)/shipments/new.tsx`

- Αφαίρεσε το πεδίο «Περίοδος φόρτωσης / εκφόρτωσης» (`loadingInfo`) από το βήμα 2 και τη γραμμή του από τη σύνοψη, για κάθε κατηγορία **εκτός** από κάδους.
- Κράτα το `loadingInfo` στο state και στο payload. Σε επεξεργασία, η παλιά τιμή πρέπει να ξανασταλεί όπως ήταν, αλλιώς σβήνεται (το `PATCH` γράφει `null` σε ό,τι λείπει).
- Τίτλος οθόνης στη δημιουργία: «Νέα Μετακόμιση» για `HOUSE_MOVE`, «Νέα Παραγγελία Κάδου» για `WASTE_BINS`, αλλιώς «Νέα Αποστολή». Στην επεξεργασία μένει όπως είναι.

### Εργασία 5 — Κατηγορία «Κάδοι Απορριμμάτων»

**Στη λίστα κατηγοριών**: `{ id: 'WASTE_BINS', icon: '🗑️', label: 'Κάδοι Απορριμμάτων', sub: 'Κάδοι και κοντέινερ απορριμμάτων' }`.

**Φόρμα όταν η κατηγορία είναι κάδος**
- Ο τίτλος κλειδώνει σε **«Προμήθεια Κάδου»** και δεν αλλάζει από τον χρήστη. Αν ο χρήστης αλλάξει κατηγορία, ο τίτλος καθαρίζει.
- Δεν υπάρχει αφετηρία. Εμφανίζονται μόνο: προορισμός (πόλη και διεύθυνση), επιθυμητή ημερομηνία παράδοσης, εκτιμώμενη διάρκεια, άλλες πληροφορίες, χωρητικότητα κάδου, παραλήπτης, περιγραφή, προϋπολογισμός.
- Κρύβονται: διαστάσεις, βάρος, όγκος, ιδιότητες (εύθραυστο, ψύξη, επικίνδυνο).
- **Εκτιμώμενη Διάρκεια**: ακέραιος 1–365, με τη λέξη «μέρες» δίπλα. Προαιρετικό.
- **Άλλες Πληροφορίες**: το πεδίο `loadingInfo` με αυτή την ετικέτα.
- **Χωρητικότητα κάδου**: επιλογή από τη λίστα, προαιρετική. Εμφάνιση «6 m³ (3,5 × 1,8 × 1 m)».

| id | m³ | Διαστάσεις |
|---|---|---|
| `3` | 3 | 2,5 × 1,5 × 0,8 m |
| `4` | 4 | 3 × 1,5 × 0,9 m |
| `6` | 6 | 3,5 × 1,8 × 1 m |
| `8` | 8 | 4 × 1,8 × 1,2 m |
| `10` | 10 | 4,5 × 2 × 1,2 m |

**Payload.** Το `POST /api/shipments` απαιτεί `originCity` και `originAddress`. Για κάδο, αντίγραψε τον προορισμό στην αφετηρία πριν στείλεις, όπως το web:

```ts
{
  ...form,
  title: 'Προμήθεια Κάδου',
  category: 'WASTE_BINS',
  originCity: form.destCity, originCityPlaceId: form.destCityPlaceId,
  originAddress: form.destAddress, originLat: form.destLat, originLng: form.destLng,
  cardDetails: { binSize: '6', durationDays: 5 },   // μόνο όσα έχουν συμπληρωθεί· αλλιώς undefined
}
```

- Πρόσθεσε το `cardDetails` στον τύπο `CreateShipmentPayload` και στον `Shipment`.
- Στην επεξεργασία, διάβασε το `cardDetails` της αποστολής και προσυμπλήρωσε χωρητικότητα και διάρκεια.
- Στη σύνοψη: γραμμές «Χωρητικότητα κάδου» και «Εκτιμώμενη Διάρκεια». Ο προορισμός μόνος του, χωρίς «→».

**Στις άλλες οθόνες**: εικονίδιο 🗑️ και ετικέτα στα `app/(tabs)/index.tsx`, `app/(tabs)/shipments/index.tsx`, `app/(tabs)/shipments/[id].tsx`. Σήμερα το `WASTE_BINS` λείπει και από τους τρεις πίνακες εικονιδίων και ετικετών.

**Αναφορά web.** `components/ShipmentForm.tsx` (όπου υπάρχει `isBins`), `lib/carrierCard.ts` (`BIN_SIZES`, `BINS_TITLE`, `normalizeBinDetails`).

### Εργασία 6 — Κάρτα μετακόμισης (θέλει την απόφαση 2)

Το μεγαλύτερο κομμάτι. Μην ξεκινήσεις πριν ο χρήστης πει αν θέλει πλήρη ή απλή έκδοση.

- Ο τίτλος κλειδώνει σε **«Μετακόμιση Οικίας/Γραφείου»**, όπως στον κάδο.
- Τα στοιχεία αποθηκεύονται στο `cardDetails` με το σχήμα `MoveDetails` του web. Ο server το καθαρίζει με το `normalizeMoveDetails`, άρα ό,τι άγνωστο πεδίο στείλεις θα χαθεί. Χρησιμοποίησε ακριβώς τα ονόματα πεδίων του web.
- Διάβασε ολόκληρο το `C:\Users\CSKIN\Fortio\lib\moveCard.ts` για τους τύπους και τις σταθερές (`FLOORS`, `HOME_TYPES`, `LIFT_OBSTACLES`, `SPECIAL_ITEMS`, `MOVE_SERVICES`, `MoveAddress`, `MoveDetails`, `emptyMoveDetails`). Μετάφερέ τα σε αρχείο του mobile, π.χ. `lib/moveCard.ts`, αντί να τα ξαναγράψεις από μνήμης.
- Οι ετικέτες είναι στο `components/i18n/el.ts` του web, στο τμήμα `moveCard`.
- Διάταξη στο web: `components/shipment-form/MoveCardFields.tsx` (φόρμα) και `components/MoveCardSummary.tsx` (σύνοψη).
- Στις λεπτομέρειες αποστολής (`app/(tabs)/shipments/[id].tsx`) δείξε τη σύνοψη της κάρτας.

## Τι δεν μεταφέρεται

- Η μπάρα της επεξεργασίας στο web (Προηγούμενη, Επόμενη, Ακύρωση) και τα κουμπιά της κεφαλίδας. Το mobile έχει τη δική του πλοήγηση.
- Όλες οι οθόνες του μεταφορέα, οι αναλύσεις φορτίων και η διαχείριση προτύπων από admin.
- Η μορφή ημερομηνίας. Το mobile χρησιμοποιεί ήδη `el-GR` (ημέρα/μήνας/έτος), που είναι αυτό που έχει πλέον και το dashboard αποστολέα του web.

## Τελικός έλεγχος

Πριν πεις ότι τελείωσες:

1. `npx tsc --noEmit` χωρίς σφάλματα.
2. Δοκίμασε σε συσκευή ή emulator, με τον χρήστη αν δεν έχεις πρόσβαση:
   - Κανονική μεταφορά: αποτελέσματα, αίτημα, και πρότυπα μόνο του είδους «Μεταφορές».
   - Μετακόμιση: κάρτες στα αποτελέσματα, αίτημα σε κάρτα, «Δεν με ενδιαφέρει», επαναφορά.
   - Κάδος: δημιουργία, επεξεργασία (χωρητικότητα και διάρκεια επιστρέφουν), εμφάνιση στο dashboard.
   - Επεξεργασία παλιάς αποστολής που είχε «Περίοδο φόρτωσης»: η τιμή δεν σβήνεται.
3. Γράψε τι δοκίμασες και τι όχι. Αν κάτι δεν δοκιμάστηκε, πες το καθαρά.
4. Γράψε τον φάκελο συνεδρίας. Στο `changes.md`, στην ενότητα API, ανέφερε την αλλαγή του `/api/routes/[id]/request` που χρειάστηκε στο Fortio.
